🔐 Multi-User Data Isolation Prevention Guide

Lessons learned from Financial 101 Master incident (May 10, 2026)

📋 The Incident

Date: May 10, 2026

Severity: CRITICAL — New users could see previous users' statement history

Root Cause: Three cascading data isolation vulnerabilities that only manifested in multi-user scenarios

Impact: Complete financial data leakage between unrelated users

Detection Method: Manual user testing (User A uploads statements → User B signs up → User B sees User A's data)

🚨 Three Vulnerabilities (All Fixed May 10)

✓ FIXED

Vulnerability #1: localStorage Persisting Across Users

Problem: Zustand store used localStorage, which persists indefinitely across browser sessions. When User A logs out and User B logs in on the same tab, User B's page load hydrates the store from localStorage—User A's cached data.

Why It's Invisible: Single-user testing works fine. Only manifests when two different users use the same browser tab.

Fix Applied: Changed storage backend from localStorage → sessionStorage in src/lib/store.ts

// BEFORE (VULNERABLE) storage: createJSONStorage(() => localStorage) // AFTER (SECURE) storage: createJSONStorage(() => sessionStorage)

Why This Works: sessionStorage clears when the browser tab closes, so each session is isolated.

✓ FIXED

Vulnerability #2: Store Not Cleared on Logout

Problem: Even with sessionStorage, if User A logs out and User B logs in on the same tab without closing it, the in-memory Zustand store still contained User A's data.

Why It's Invisible: Most test scenarios either: (a) close the browser between users, or (b) don't fully logout.

Fix Applied: Added clearStore() function called from clearSession() in src/lib/auth.ts

// NEW: Clear store when user logs out export function clearStore() { useStore.setState({ transactions: [], statementImports: [], // ... reset all data to defaults }); sessionStorage.removeItem("financial-planner-storage-v3"); }
✓ FIXED

Vulnerability #3: All Users Sharing Same Account ID (ROOT CAUSE)

Problem: The getCurrentAccount() function returned a hardcoded account with id="toy". This meant ALL transactions from ALL users were assigned the same accountId.

// BEFORE (VULNERABLE) export const MAIN_ACCOUNT = { id: "toy", // Hardcoded! Every user gets this name: "Toy Theeranan", }; export function getCurrentAccount() { return MAIN_ACCOUNT; // Same for all users! }

When transactions were filtered in /expenses/actuals:

const transactions = store.transactions.filter( t => t.accountId === activeAccountId // activeAccountId always "toy" ); // Result: ALL users see ALL transactions with accountId="toy"!

Why It's Invisible: The code looks correct—there IS filtering by accountId. The bug is that the filter value is the same for everyone.

Fix Applied: Changed getCurrentAccount() to return per-user account in src/lib/accounts.ts

// AFTER (SECURE) export function getCurrentAccount(): Account { const session = getSession(); return { id: session.userId, // Unique per user! name: session.username, role: session.role, // ... }; }

Why This Works: Each user has a unique userId from Supabase. Transactions are now scoped to that unique ID.

🛡️ Prevention Framework

1. Multi-User Integration Tests (Most Important)

Test Pattern: Every feature that touches user data needs a 2+ user test

describe("Per-user data isolation", () => { test("User A cannot see User B's transactions", async () => { // Step 1: Login as User A const userA = await loginAs("userA@test.com"); // Step 2: User A imports statement (10 transactions) const stmt = await importStatement(userA, testPdf); expect(stmt.transactionCount).toBe(10); // Step 3: CRITICAL - Switch to User B const userB = await loginAs("userB@test.com"); // Step 4: Verify User B sees ZERO transactions const txns = await fetchTransactions(userB); expect(txns).toHaveLength(0); // MUST be empty! // Step 5: User B imports different statement (8 transactions) const stmtB = await importStatement(userB, testPdf2); expect(stmtB.transactionCount).toBe(8); // Step 6: Verify User A still sees ONLY their 10 await loginAs("userA@test.com"); const txnsA = await fetchTransactions(userA); expect(txnsA).toHaveLength(10); }); });

2. Code Review Checklist

  • All database queries: Does SELECT/INSERT/UPDATE filter by userId or accountId? NO WHERE clause = automatic red flag
  • Cache keys: If storing in localStorage/sessionStorage, is the key scoped to user? Never "app_data", always "app_data_${userId}"
  • Default values: Is there a fallback that could leak old data? (e.g., hardcoded account ID)
  • Logout handler: Does it clear ALL user state? Store, cache, cookies, etc.
  • API authorization: Does /api/sync verify the user can only access their own storageKey? Validate on server side
  • Multi-user test: Does the PR include a test with 2+ users? If not, request it

3. Common Blindspots

  • Global state that should be per-user: Hardcoded IDs, single-user defaults, shared accounts
  • Persistent caches without user scope: localStorage keys that don't include userId
  • Filters that look correct but use wrong value: Code filters by accountId but accountId is hardcoded to same value for all users
  • Missing logout side effects: Session cleared but in-memory state not cleared
  • Initialization bugs: New user inherits previous user's data on page load because store hydrates before user is authenticated

4. Critical Files to Always Audit

src/lib/store.ts — Storage backend (localStorage vs sessionStorage), clearStore() function
src/lib/auth.ts — clearSession() must call clearStore(), getSession() must be accurate
src/lib/accounts.ts — getCurrentAccount() must return per-user account, not hardcoded value
src/app/api/sync/route.ts — Must authenticate user and validate they can only read/write their storageKey
src/app/expenses/actuals/page.tsx — Verify transactions are filtered by activeAccountId, not a constant
Any localStorage.setItem() calls — Convert to sessionStorage or scope key by userId

📊 Monitoring & Detection

Post-Deployment Alerts:
  • User reads/writes to storageKey that doesn't match their session
  • Same transaction ID appears for multiple users
  • Query returns data from different accountId than requested user's

✅ Verification After Deploy

  • Fresh account created → verify zero statements (not admin's statements)
  • User A imports statement → User B logs in → User B sees zero statements
  • Logout in same tab → Login as different user → verify data cleared
  • Browser DevTools: Check sessionStorage is cleared on logout
  • API test: Attempt to read another user's storageKey → expect 403 Forbidden

🎓 Key Lessons

1. Data isolation issues hide in multi-user scenarios: Single-user testing misses them completely.

2. Hardcoded values are dangerous: MAIN_ACCOUNT.id = "toy" looked like a constant but was a shared resource.

3. Visible code isn't always correct: The filtering code looked right even though the filter value was wrong.

4. Cache + User logout = data leakage: Stores that aren't cleared explicitly on logout carry data between users.

5. Detection requires intentional testing: This issue only appeared when deliberately testing with two users in the same session.
